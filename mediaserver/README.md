# mediaserver

A Go replacement for the PictShare (PHP) service, see `../REWRITE_PLAN.md`. Same URLs, same data directory layout,
same S3 keys and same upload API, so it can run next to PictShare on the same volume and bucket, and rolling back is
switching the container back.

One static binary, with `vips` (libvips CLI), `ffmpeg`/`ffprobe` and `file` from Alpine. Each external tool runs with a
timeout and `ulimit -v`, so a bad input can only fail its own request.

## Layout

| Package | What |
|---|---|
| `cmd/mediaserver` | env config, startup, graceful shutdown |
| `internal/hashcodec` | dimension-encoding hashes (AES-256-CBC, base62), golden tests generated with the PHP code |
| `internal/store` | `data/<hash>/<hash>`, variants, `deletecode`, `sha1.csv`; atomic writes; read-only overlay |
| `internal/imaging` | type sniffing, JPEG normalisation at upload (EXIF orientation applied, metadata stripped), resize / rotate / forcesize / webp variants |
| `internal/video` | ffprobe-based normalisation plan (ported from `video.controller.php`, checked against it on the corpus), remux / transcode, preview frames, gif to mp4 |
| `internal/s3store` | S3 get / put / delete (aws-sdk-go-v2) |
| `internal/server` | HTTP: URL grammar (`architect`), upload / geturl / info API, coub / vimeo, serving with ETag / Range / 304, S3 restore and upload queue |
| `difftest/` | differential test against the PHP stack (below) |

## Behaviour

- **URLs**: everything PictShare served in production: `/<hash>`, `/<size>/`, `/w/<n>/`, `NxM`, `left` / `right` / `upside`,
  `forcesize`, `webp`, `/raw/`, `/preview/[<w>/]`, `/download/`, `/delete_<code>/`, gif `/mp4/`, `/coub/<id>`, `/vimeo/<id>`,
  segments in any order. Variant files keep PictShare's names (`md5(http_build_query(...))_<hash>`), so variants
  generated by either service are reused by the other.
- **Dropped**: the colour filters (`sepia`, `vintage`, ...: the segment is ignored and the picture is served without it),
  `/api/base64.php`, `/api/pastebin.php`. Query strings are ignored.
- **API**: same JSON fields and reason strings as PictShare, except an oversized upload gets
  `{"status":"err","reason":"File too big. 50mb max"}` instead of an nginx 413 page. Every `/api/*` request needs
  `Authorization: Client-ID <CLIENT_ID>`; Caddy checks it, and so does the service. `geturl` fetches only from public
  addresses, with a size cap, a timeout and a redirect limit.
- **Images**: JPEG uploads are re-encoded with the orientation applied (all 8 EXIF orientations) and metadata
  stripped. Untagged CMYK JPEGs are converted with the plain formula, as browsers and GD do. PNG / GIF / WebP are
  stored as uploaded. Resampling is libvips instead of GD: same sizes, pixels differ slightly.
- **Video**: as documented in `../CLAUDE.md` ("Video Pipeline"). Container and audio fixes happen synchronously,
  before the URL is returned, and transcodes run in the background. Concurrency is bounded by in-process semaphores
  (`MAX_CONCURRENT_VIDEO_HANDLERS`) instead of lock files.
- **Caching**: strong ETag (inode-mtime-size) and Last-Modified on files, `Cache-Control: public, max-age=31536000`
  on success, `no-store` on every error. Range, If-Range, If-None-Match and If-Modified-Since come from Go's `http.ServeContent`.
- **S3**: on a local miss, the original is restored from the bucket. Only names this service could have produced are
  looked up: dimension hashes must decrypt with the key, other names are rate limited, and misses are cached.
  Uploads go to S3 from a background queue: a marker per pending file in `data/.s3-pending/` (which the
  cleanup service's `ls` doesn't see), retries with backoff, and a sweep at startup. An S3 outage delays the copy, not
  the upload.
- **Read-only mode** (`READ_ONLY=1`): never writes to the data directory. Uploads and deletes return 503. Files
  restored from S3 and generated variants go to a scratch overlay, which is cleared at startup. Used to run next to
  PictShare for comparison.

## Configuration

| Variable | Default | |
|---|---|---|
| `HASH_DIMS_AES_KEY` | | as for PictShare; empty = random names |
| `CLIENT_ID` | | required for `/api/*` |
| `MAX_UPLOAD_SIZE` | 50 | MB |
| `CONTENTCONTROLLERS` | all | `IMAGE,VIDEO,TEXT` subset accepted by `upload.php` |
| `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_ENDPOINT` | | empty bucket = no S3 |
| `COUB_PROXY_URL` | | as for PictShare |
| `MASTER_DELETE_CODE`, `MASTER_DELETE_IP` | | empty = disabled |
| `MAX_CONCURRENT_VIDEO_HANDLERS` | 4 | ffmpeg runs (remux, transcode, previews of gif->mp4) |
| `MAX_CONCURRENT_IMAGE_HANDLERS` | 2 | vips / preview renders |
| `FFMPEG_MEMORY_LIMIT_MB` | 2560 | `ulimit -v` per ffmpeg / ffprobe |
| `VIPS_MEMORY_LIMIT_MB` | 1024 | `ulimit -v` per vips run |
| `MAX_IMAGE_MEGAPIXELS` | 200 | larger images are refused |
| `READ_ONLY` | | `1` = read-only mode (above); `OVERLAY_DIR` for its scratch space |
| `TOUCH_ON_ACCESS_MINUTES` | 0 | > 0: bump a hash directory's mtime when served (at most this often), so the cleanup service evicts by last use instead of upload time |
| `DATA_DIR`, `TMP_DIR`, `STATIC_DIR`, `LISTEN` | `/var/www/data`, `/tmp/mediaserver`, `/srv/static`, `:80` | |
| `URL`, `TITLE` | | prefix of returned URLs (empty in production), page title |

The container runs as uid 100 / gid 101, the `nginx` user of the PictShare image, so both can write the volume.

## Build and test

```bash
# from the repository root
docker build -f mediaserver/Dockerfile --target test .   # go vet + unit and HTTP tests with real vips/ffmpeg
docker build -f mediaserver/Dockerfile -t orbitar-mediaserver .
docker compose --profile mediaserver up -d mediaserver    # next to pictshare, read-only by default
```

### Differential test against PictShare

`difftest/` runs both stacks behind the repository's Caddyfile (PHP on :8443, Go on :8445) with a shared s3mock,
uploads a synthetic corpus to both and compares every URL shape: status, content type, cache headers, image size
and pixels (RMSE), ffprobe of the stored videos, Range responses, and the API answers. A second step checks that Go,
started on an empty data directory, restores PictShare's uploads from S3 byte for byte, and that read-only mode leaves
PictShare's data directory untouched. It never talks to a real bucket.

```bash
export DIFF_WORK=$(mktemp -d) PHP_IMAGE=orbitar-media-pictshare GO_IMAGE=orbitar-mediaserver
export CLIENT_ID=$(grep ^CLIENT_ID= .env | cut -d= -f2-)
mediaserver/difftest/corpus.sh $DIFF_WORK/corpus          # needs magick, exiftool, ffmpeg
mediaserver/difftest/stack.sh up
mediaserver/difftest/diff.py $DIFF_WORK/corpus $DIFF_WORK/work
mediaserver/difftest/restore_readonly.sh $DIFF_WORK/corpus
mediaserver/difftest/stack.sh down
```

Last run (PHP 8.4 image vs this service): video plans and outputs identical on all 21 accepted videos, all 41 uploads
restored byte for byte, no writes in read-only mode. The remaining differences are inputs where PictShare fails and the
Go service doesn't (EXIF orientation 5, animated WebP and truncated PNG variants, a 7000x7000 JPEG and the
rotation of a 3000x5000 one hitting PHP's memory limit), plus the intended ones listed above.

## Cutover

1. Run `mediaserver` next to `pictshare` read-only (the compose profile's default) behind a second Caddy route,
   e.g. a `go.{$SERVER_DOMAIN}` site with `reverse_proxy http://mediaserver:80` and the same Client-ID rule. Replay a
   day of production GETs against both and diff. Keep this step short: the overlay (S3 restores, variants) lives in
   the container and is not seen by the cleanup service.
2. Set `MEDIASERVER_READ_ONLY=0` and switch Caddy's GET traffic to `mediaserver`, keeping `/api/*` on `pictshare`; a
   week. Both services may now write the volume: variants have the same names and are renamed into place, `sha1.csv`
   is appended under `flock` by both, and uploads still only reach PictShare.
3. Route `/api/*` to `mediaserver` as well. Optionally set `MEDIASERVER_TOUCH_ON_ACCESS_MINUTES` (e.g. 60) for
   last-use eviction. Keep the PictShare image for rollback: data and S3 layout are unchanged, so rollback is a Caddy
   change.
4. Bunny: nothing to purge; existing files keep their bytes, new ETags only appear for newly generated variants.
5. Remove PictShare from the repository.
