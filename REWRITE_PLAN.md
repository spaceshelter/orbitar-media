# Plan: replace PictShare (PHP) with a small Go service

Status as of 2026-10-22: plan only, nothing started. The PHP 8.4 upgrade (`PHP_UPGRADE_PLAN.md`) ships first and stays the
fallback until cutover.

## Why

- No PHP patch treadmill: one static binary plus libvips and ffmpeg.
  Fewer CVEs to track on the runtime side.
- Memory: libvips streams and shrinks while decoding, so a 24 MP photo resize needs tens of MB instead of GD's
  2-3 full-size buffers (the reason `PHP_MEMORY_LIMIT` had to go to 256). No php-fpm pool of 25 x 256 MB.
- One process handles uploads, serving and background work, so concurrency limits are in-process semaphores
  instead of flock'd slot files, and atomic writes and ETags are written once and used everywhere.
- The PHP codebase is mostly dead weight: prod uses a small part of it (see below).

same resize/rotation), not 404, so any old embed keeps showing the picture.

## Stack

- **Go** (net/http, `http.ServeContent` for Range/If-Range/304/ETag, which replaces `parseByteRange()` and `statETag()`).
- **libvips** via `govips` (or `bimg`): decode with shrink-on-load, auto-rotate from EXIF, strip metadata, resize,
  rotate, encode JPEG/PNG/WebP. Animated GIF passes through untouched as today.
- **ffmpeg/ffprobe** via `exec.CommandContext` with a timeout and `ulimit -v` (or `prlimit`), same caps as today.
  The probe-based normalisation plan in `video.controller.php` (`planNormalization`) ports almost line for line.
- **aws-sdk-go-v2** for S3.
- Image: Alpine or distroless with vips + ffmpeg, ~150 MB. Caddy and the cleanup container stay as they are.

## Compatibility (must be byte-for-byte or behaviour-identical)

Existing URLs are embedded in years of Orbitar posts and cached by Bunny; the data directory and the S3 bucket are
shared with the PHP version so that rollback is just switching the container back.

- **Hash format**: dimension-encoding hashes are AES-256-CBC with `HASH_DIMS_AES_KEY`, the 8-byte IV doubled to 16,
  a leading `1` version byte, GMP base62 alphabet. Plain random hashes for old uploads. Port it with golden tests
  generated by the PHP code (encode in PHP, decode in Go and back) before anything else.
- **Storage layout**: `data/<hash>/<hash>`, variants in the same directory with today's file names (so the cache and
  the cleanup service keep working), `data/<hash>/deletecode`, `data/sha1.csv` (append-only `sha1;hash` lines, same
  format, used for dedupe), `coub_cache` files.
- **S3 keys**: the bare hash; on a local miss, fetch from S3 and restore into `data/<hash>/`.
- **URL grammar**: every form in the table above, segments in any order (`/300/left/x.jpg` == `/left/300/x.jpg`),
  `/w/N`, `NxM`, `/raw`, `/preview/`, `/download/`, `/delete_<code>/`. Write a URL parser test table from the prod
  access log (distinct shapes, not hashes).
- **API responses**: upload JSON fields (`status`, `hash`, `filetype`, `url`, `delete_code`, `delete_url`, plus error
  `reason` strings Orbitar shows), info.php fields. Orbitar's client is the contract: check `orbitar` repo for the
  fields it reads.
- **Headers**: strong ETags and `Last-Modified` as introduced in #11, long `Cache-Control` on success, `no-store` on errors.

## Don't carry over

- The S3 upload retry queue is written but never drained: retry in-process with backoff, and a startup sweep.
- Cleanup evicts by mtime, so a hot old file goes before a cold new one: evict by last use (can be done in the
  cleanup service later).
- Input validation and resource limits are designed in from the start (hash format checked before any storage lookup,
  bounded variant sizes, bounded outbound fetches) rather than ported from PictShare's behaviour.
- Every generated file goes to a temp name and is renamed into place (already true in PHP after this upgrade).

## Work breakdown

| Area | Estimate |
|---|---|
| Hash codec + golden tests, URL parser, upload API, sha1 dedupe, delete codes, info/geturl | 3-4 d |
| Images: libvips pipeline, EXIF orientation, resize/rotate/webp, variant cache | 2-3 d |
| Video: probe + normalise plan, remux at upload, background transcode queue, preview frame, Range serving | 2-3 d |
| S3 (restore on miss, upload with retry), coub/vimeo pages, txt | 1-2 d |
| Differential testing against the PHP stack, cutover | 2-3 d |
| **Total** | **~2-3 weeks** |

The differential harness used for the PHP upgrade (old vs. new stack, same corpus sampled from prod, compare status,
headers, decoded pixels with RMSE, ffprobe output) is the acceptance test; expect pixel differences from libvips vs. GD
resampling, so compare images with a tolerance and spot-check by eye.

## Cutover

1. Run the Go service next to PictShare on the same data volume, read-only (no writes, no cleanup interplay), behind a
   second Caddy route; replay a day of prod GETs against both and diff.
2. Switch Caddy's GET traffic to Go; uploads still go to PHP. A week.
3. Switch uploads. Keep the PHP container image around for rollback; data and S3 layout are unchanged, so rollback
   is a Caddy change.
4. Bunny: nothing to purge if responses stay identical; new ETags only appear for newly generated variants.
5. Remove PictShare from the repo.
